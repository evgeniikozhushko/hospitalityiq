The next milestone should be a trustworthy guest-review pilot: load real reviews for 2–3 properties and reliably answer both “what are guests saying?” and “how often is this happening?”

The app already has a working single-question chat, streamed answers with sources, review ingestion, and an evaluation harness. Its main gap is that the current data and evaluation use a small fictional fixture, while the planned pilot depends on real reviews, accurate counts, and trends.

I’d prioritize development in this order:

1. Finish and evaluate the current answer improvements. There are uncommitted changes to filtering, planning, answer handling, and evaluation cases. Review and test those first, then run a fresh baseline. The last saved baseline passed 19 of 25 questions across three runs; the failures included grounding, verbatim quotes, and acknowledging evidence limits. Its perfect retrieval scores are encouraging but come from only eight fictional reviews.
2. Bring in real review data. Obtain exports for 2–3 pilot properties and build a repeatable import with validation, deduplication, property mapping, and an import report. The project notes say Google Business Profile API access is pending, so CSV imports can unblock development. Confirm the permitted data sources and handling with the team before using non-public exports.
3. Build the structured review and theme layer. Agree on a practical theme taxonomy with marketing, store reviews and tags in Postgres, and validate tagging against a hand-labelled sample. Then implement exact counts and period comparisons. This unlocks the core question, “What are guests complaining about most?”, without treating retrieved examples as a representative count.
4. Evaluate against real marketing questions. Label relevant reviews for roughly 20 questions and measure retrieval, citations, grounding, and theme accuracy. Use the results to decide whether hybrid search and reranking materially improve on the current dense search.
5. Make it pilot-ready. Add authentication and access controls before deployment, along with operational basics such as error monitoring, cost visibility, and a supported way to refresh reviews. Test the workflow with the marketing partner and capture feedback.
6. Add campaign memory after the review workflow is reliable. Campaigns are part of the stated pilot scope, so they shouldn’t disappear from the roadmap. Start with a small set of structured campaign records and make sure financial figures have role-based access before exposing them in answers.
7. Build persistent conversation history: A larger feature requiring a database, user accounts or another ownership model, history management, and decisions about whether follow-up questions use earlier messages. That fits naturally alongside the planned Postgres and authentication work.
